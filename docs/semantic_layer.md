# Semantic layer: how a metric is defined once and proven

The semantic layer is built with [MetricFlow](https://docs.getdbt.com/docs/build/about-metricflow)
on dbt Core 1.12 over Snowflake. Each metric is defined **once**, in YAML next to the mart
it reads from. Every consumer (Power BI, the AI agent, the command line) asks for the
metric by name, and MetricFlow writes the SQL, including the business rule and any joins.

This page walks through two metrics end to end: definition → generated SQL → result → proof.

## How the tables connect

MetricFlow joins tables through **entities** (shared keys). No join is written by hand.

```
             customers (customer)          products (product)
                    ▲                              ▲
                    │ customer                     │ product
   sessions ◄─── orders (sales_order) ◄─── order_items (order_item)
   (session)        │ campaign
                    ▼
             campaigns (campaign)
```

| Semantic model | dbt model | Primary entity | Default date |
|---|---|---|---|
| orders | fct_orders | sales_order | order_date |
| order_items | fct_order_items | order_item | order_date |
| customers | dim_customers | customer | signup_date |
| products | dim_products | product | — |
| sessions | fct_web_sessions | session | session_date |
| campaigns | dim_campaigns | campaign | start_date |

> The orders entity is named `sales_order`, not `order`: `ORDER` is a reserved word in
> Snowflake and broke MetricFlow's validation queries.

## Metric 1: `net_revenue` (a business rule, applied automatically)

**Business definition:** revenue net of promo discounts, from **recognized** orders only
(status completed or shipped). Placed, returned and cancelled orders are excluded.

**Definition** (`models/marts/core/_fct_orders.yml`):

```yaml
- name: net_revenue
  label: Net revenue
  type: simple
  agg: sum
  expr: net_amount
  filter: "{{ Dimension('sales_order__is_recognized') }} = true"
```

**Query:**

```bash
mf query --metrics orders,net_revenue --group-by sales_order__order_status --decimals 2
```

**Result:**

| order status | orders | net_revenue |
|---|---:|---:|
| completed | 780,180 | 770,347,xxx |
| shipped | 79,759 | 78,933,xxx |
| placed | 39,927 | — |
| returned | 60,154 | — |
| cancelled | 39,980 | — |

`orders` counts every status; `net_revenue` exists only for completed and shipped.
Nobody querying `net_revenue` can include a cancelled order by mistake.

## Metric 2: `product_net_revenue` (automatic joins, and two tables that agree)

**Business definition:** the same recognized net revenue, calculated per **order line**,
so it can be split by product category, brand and price tier.

**Definition** (`models/marts/core/_fct_order_items.yml`):

```yaml
- name: product_net_revenue
  label: Product net revenue
  type: simple
  agg: sum
  expr: line_net_amount
  filter: "{{ Dimension('order_item__order_status') }} in ('completed', 'shipped')"
```

**Query: revenue by category** (category lives in `dim_products`; MetricFlow joins on `product`):

```bash
mf query --metrics product_net_revenue,units_sold --group-by product__category --order -product_net_revenue --decimals 2
```

| category | product_net_revenue | units_sold |
|---|---:|---:|
| Apparel | 136,969,521.83 | 669,434 |
| Books | 116,902,505.04 | 567,507 |
| Sports | 103,919,155.44 | 473,761 |
| Home | 102,689,253.06 | 520,221 |
| Electronics | 101,971,737.19 | 568,810 |
| Toys | 101,487,410.75 | 508,032 |
| Grocery | 96,037,056.06 | 511,404 |
| Beauty | 88,969,744.59 | 480,940 |
| **Unknown** | **334,126.51** | **1,694** |
| **Total** | **849,280,510.47** | |

**The Unknown row is deliberate.** About 1,000 order lines reference products that
weren't in the catalog yet (late-arriving data). Instead of an inner join that silently
drops them, they map to an *Unknown product* member (`product_id = -1`), so their
$334K of recognized revenue stays in every total. See [data_quality.md](data_quality.md), issue #9.

## Proof: two tables, one number

`net_revenue` is computed from **orders**; `product_net_revenue` from **order lines**.
If the layer is correct, they must match exactly in every period:

```bash
mf query --metrics net_revenue,product_net_revenue --group-by metric_time__year --order metric_time__year --decimals 2
```

| year | net_revenue | product_net_revenue |
|---|---:|---:|
| 2023 | 26,193,720.35 | 26,193,720.35 |
| 2024 | 233,196,878.43 | 233,196,878.43 |
| 2025 | 322,122,806.86 | 322,122,806.86 |
| 2026 | 267,767,104.83 | 267,767,104.83 |
| **Total** | **849,280,510.47** | **849,280,510.47** |

The two metrics agree to the cent, and the category breakdown above sums to the same
total. This is also enforced on every build by the singular test
`tests/assert_line_revenue_ties_to_orders.sql`.
